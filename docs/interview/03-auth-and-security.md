# 3. 开放 API 请求链路与安全

本章是项目最容易被深挖的部分。建议先完整讲一遍请求链，再针对签名、防重放、SSRF 和敏感数据展开。

## 3.1 一次开放请求的执行顺序

```text
HTTP 请求
  → TraceIdFilter：生成 traceId，写入日志上下文和响应头
  → SignatureFilter：检查 body 大小、签名头、时间戳和 App 状态
  → IP 白名单 → HMAC 验签 → Redis SETNX 消费 Nonce
  → 查询已发布 API、ACTIVE 订阅和配额套餐
  → Redis Lua 检查 QPS，再用另一段 Lua 检查日/月额度
  → 将已验证的 appId、API、traceId 放进 request attribute
  → OpenApiController 调用 OpenApiProxyService
  → 校验上游地址、转发 HTTP 请求、按敏感级别处理响应
  → SignatureFilter finally 收集状态、耗时、大小并发送调用日志
```

遇到任何前置业务异常时，过滤器构造统一错误响应；早期失败可能尚未识别 appId 或 apiId，因此调用日志里的对应字段允许为空。`ContentCachingResponseWrapper` 让过滤器能够读取响应状态和字节数，结束前必须 `copyBodyToResponse()`，否则缓存的响应不会发给客户端。

## 3.2 HMAC 签名怎么解释

当前规范串是：

```text
METHOD\nPATH\nSORTED_QUERY\nTIMESTAMP\nNONCE\nSHA256_HEX(body)
```

调用端和服务端必须对 HTTP 方法、路径、Query 参数排序/编码、时间戳、Nonce 和原始请求体得到完全相同的规范字符串，再用 AppSecret 计算 HMAC-SHA256。签名覆盖请求体摘要，防止攻击者只替换 Body 而沿用原签名；覆盖路径和 Query，防止把签名挪用到其他资源。

HMAC 是带密钥的消息认证码，不是加密。客户端不发送 Secret，只发送签名；服务端取回 Secret 重新计算结果，并用常量时间比较，降低比较过程产生时间侧信道的风险。

### 为什么需要缓存请求体？

HTTP 请求体通常是一次性流。验签过滤器先读取原始字节后，Controller 或代理服务还需要读取同一请求体。`CachedBodyHttpServletRequest` 在大小上限内缓存字节并提供可重复读取能力；超出 `max-body-bytes` 的请求直接拒绝，避免无限制占用内存。签名必须针对原始字节计算，不能先把 JSON 解析再序列化，因为字段顺序、空格和编码差异会改变内容。

### 为什么要把 Query 参数排序？

同一组 Query 参数在 URL 中可以有不同排列；如果不规范化，调用端和服务端会因顺序差异算出不同签名。当前实现按参数 key/value 排序并统一编码。多值参数也需要双方采用相同排序规则。

## 3.3 时间戳与 Nonce 如何防重放？

- 时间戳窗口限制请求有效时间，当前默认允许服务器时间前后 300 秒，缩小攻击者可重放的时间范围。
- Nonce 是一次性随机标识。签名通过后，服务端使用 `SETNX` 并设置 5 分钟 TTL；同一 App 在窗口内重复使用同一 Nonce 会被拒绝。
- 必须验签成功后再占用 Nonce，避免无效请求预先占用合法随机串。
- Nonce key 按 AppKey 隔离，避免不同 App 之间互相冲突。

面试时要指出：系统节点时钟必须同步；Nonce 去重依赖 Redis 可用性；跨地域部署时要考虑时钟偏差、Redis 分区和存储容量。高安全场景还可把请求 ID、业务幂等键和签名有效期策略结合起来。

## 3.4 登录 Token 与 AK/SK 的区别

| 项目 | 控制台登录 Token | 开放 API 的 AK/SK |
|---|---|---|
| 使用者 | 人类用户登录控制台 | 程序/应用调用开放能力 |
| 凭证形态 | 随机 Token，在 Redis 中关联用户快照 | AppKey 定位应用，AppSecret 用于 HMAC 签名 |
| 生命周期 | 滑动 TTL，登出删 Redis key | Secret 长期使用，可由开发者重置并清缓存 |
| 授权粒度 | 登录用户角色和资源归属 | App 对 API 的 ACTIVE 订阅及配额 |
| 本项目入口 | MVC 拦截器 | `/openapi/**` 的 `SignatureFilter` |

用户密码采用 BCrypt，因为校验只需要比较哈希；AppSecret 必须被服务端取回参与 HMAC，因此数据库采用 AES-GCM 可逆加密存储。两种凭证不能用同一种存储策略。

## 3.5 上游代理与 SSRF

API 管理员可以配置上游 URL，因此它是服务器端主动发起的网络请求入口，必须防止 SSRF。当前实现对 URL 限制 HTTP/HTTPS、拒绝 userinfo，并解析 DNS 检查回环、私网、链路本地、CGNAT 等地址；每次转发前重新校验，禁止跟随重定向，并配置为不继承系统代理。`allow-loopback` 只用于受控本地演示，生产环境应关闭。

仍需诚实说明边界：DNS 校验和实际连接之间存在 TOCTOU/DNS 重绑定风险；如果允许用户配置任意上游，生产部署还应使用网络出口 ACL、域名/IP 白名单、受控代理或固定解析/连接策略，并限制响应大小、连接数和超时。当前 `RestTemplateConfig` 使用全局连接和读取超时配置；`ApiDefinition.timeoutMs` 虽然存在，但代理并未按每个 API 动态应用它。

### 为什么禁止跟随重定向？

如果上游返回 302 指向内网地址，而 HTTP 客户端自动跟随，首次校验的目标 URL 可能安全，最终请求却访问了内网服务。禁止跟随重定向可避免这一跳绕过目标检查；若业务必须支持重定向，应对每一跳重新执行完整 URL 和目标 IP 校验。

## 3.6 敏感响应脱敏

API 定义中有敏感级别。代理服务根据级别处理 JSON 响应，针对订单、用户等示例 API 对手机号、邮箱、地址、身份证等字段脱敏。应区分两种安全目标：

- **对调用方返回**：按 API 敏感等级限制响应中的敏感字段暴露。
- **写日志与审计**：尽量只保存必要的元信息；审计参数截断不等于脱敏，敏感 DTO 不应进入审计参数序列化。

如果响应不是可解析 JSON，或结构与脱敏规则不匹配，需要定义明确的失败策略；敏感 API 可考虑失败关闭，避免原样返回未脱敏内容。

## 3.7 安全类追问题

### 为什么不能把 AppSecret 单向哈希？

服务端没有办法从单向哈希恢复原密钥，无法重新计算 HMAC。AppSecret 需要可逆加密保存；主密钥单独由环境变量/密钥管理服务提供，数据库只保存密文。用户密码则只需验证，不需要恢复明文，所以使用 BCrypt。

### 常量时间比较解决什么问题？

普通字符串比较可能在遇到第一个不相同字符时提前结束，响应时间会随匹配前缀长度变化。常量时间比较尽量让比较耗时与匹配位置无关，减少攻击者通过大量采样推断签名字符的机会。

### `X-Forwarded-For` 可以直接作为客户端 IP 吗？

不可以，它可以由客户端伪造。默认应使用 TCP 对端地址；只有应用部署在可信反向代理后，并由代理覆盖或清洗转发头时，才开启代理信任配置。还要限制哪些代理地址有权提供转发头。

### 配额什么时候扣？上游失败会退吗？

当前在上游调用之前扣 QPS 令牌和日/月额度；上游超时、5xx 或网络失败不会自动返还。这样实现简单且能限制尝试流量，但会让失败请求也消耗配额。要支持返还，需要设计预占、结果确认、补偿、并发安全以及进程崩溃恢复，不能只在 catch 里随手加回计数。
