# 4. MySQL、Redis 与并发一致性

## 4.1 关系模型与索引

数据库围绕“用户—应用—API—订阅—调用”建模。`tb_subscription` 用 `(app_id, api_id)` 联合唯一索引保证同一应用对同一 API 只有一条订阅；`tb_call_log.trace_id` 唯一，供日志幂等；`tb_usage_stat(app_id, api_id, stat_date)` 唯一，支持按日聚合 upsert。调用日志有按 app/API 与时间组合的索引，匹配控制台常见筛选。

### 为什么业务检查之外还要唯一索引？

先查再插无法防止并发竞态：两个线程都查到记录不存在，然后都执行插入。应用层检查可以给友好错误提示，但数据库唯一约束才是并发下的最终裁判。项目在订阅、用户名、API code 等业务上会捕获重复键异常并映射为业务错误。

### 联合索引的最左前缀是什么？

联合索引 `(a,b,c)` 通常可支持从 `a` 开始的连续前缀条件，如 `a`、`a+b`、`a+b+c`；只过滤 `b` 通常不能直接充分利用该索引。索引设计应根据真实 where/order by 和选择性评估，并用 `EXPLAIN` 验证，避免盲目增加索引造成写放大。

### 如何防止越权查询？

不能只信任客户端传来的 appId。项目会从 `UserHolder` 获取当前用户，再通过 `getOwnedApp` 核对应用归属，然后才查询或修改相关订阅、应用、日志。分页查询开发者日志时把归属 App 范围固定在 Service 侧，避免用户通过改 URL 参数看到别人的数据。

## 4.2 状态机与并发更新

API 状态主要是 `DRAFT → PUBLISHED → OFFLINE → PUBLISHED`；订阅状态包括 `PENDING → ACTIVE/REJECTED`，拒绝后可以重新进入 `PENDING`。枚举表达允许的业务转换，Service 负责校验，数据库条件更新负责并发防护。

典型做法：

```sql
UPDATE tb_api
SET status = 'PUBLISHED'
WHERE id = ? AND status = 'DRAFT';
```

受影响行数为 0 表示记录不存在、状态已变化或并发更新已先完成，应返回冲突/状态异常，而不是继续假设本次转换成功。这是乐观并发控制的一种实现，避免“先查状态、后无条件更新”导致后写覆盖前写。

## 4.3 Cache Aside 与缓存问题

项目的业务查询采用 Cache Aside：先查 Redis，未命中后查 MySQL，再回填 Redis；写操作先更新数据库，再删除相关缓存。Redis 主要缓存 App 鉴权信息、API 定义和有效订阅。

缓存组件还实现了：

- **空值缓存**：未查到对象时写短 TTL 空值标记，减少穿透。
- **互斥重建**：热点 key 过期时用 Redisson 锁控制缓存重建，并在获得锁后再次查缓存。
- **TTL 抖动**：基础过期时间增加随机抖动，减少同批缓存同时失效。
- **缓存失效**：修改 Secret、IP 白名单、API 状态/定义、订阅状态后删除相应 key。

### 缓存击穿、穿透、雪崩分别是什么？

- **穿透**：请求一直查不存在的数据，缓存无法命中，每次都打数据库；可用参数校验、空值缓存、布隆过滤器。
- **击穿**：热点 key 失效瞬间大量请求同时回源；可用互斥重建、逻辑过期或请求合并。
- **雪崩**：大量 key 同时过期或 Redis 故障导致集中回源；可用 TTL 抖动、分级缓存、限流与降级。

要准确描述当前代码：锁获取失败后短暂等待再查缓存；缓存仍未建立时仍可能直接回源，因此它是降低击穿风险，不是保证绝对只有一个线程回源。锁租期有限，回源时间超过租期也可能再次并发重建。

### 为什么通常先更新数据库，再删除缓存？

缓存值可以从数据库重建，更新 DB 后删除缓存更容易保持最终一致。直接先写缓存再更新 DB 可能在 DB 失败时留下错误值。并发下“更新 DB、删除缓存”仍可能有旧值回填竞态；严格场景可用延迟双删、版本号、消息失效、逻辑过期等方案，具体需要根据一致性要求和请求量权衡。

## 4.4 Redis Lua 与限额设计

### 令牌桶如何限流？

令牌按固定速率补充，桶最多保存 `capacity` 个令牌；每个请求消耗令牌，令牌不够就拒绝。桶容量允许短时突发，长期平均速率受补充速率限制。项目 key 按 `appId:apiId` 隔离，Lua 在 Redis 单次脚本执行内完成读令牌、补充、判断和扣减。

### 为什么脚本比客户端多条命令更安全？

如果在客户端分开执行“读计数—比较—加一”，两个并发请求可能都读取到剩余额度并同时通过。Lua 脚本在 Redis 执行期间作为一个原子操作，避免同一份计数被并发交错修改。

### 日/月配额为什么和 QPS 放在同一个 Lua？

脚本一次完成令牌桶与日/月计数：令牌不足返回 0，日/月任一达上限返回 -1/-2，只有全部通过才扣令牌并同时递增日、月计数，避免“令牌已扣但配额不足”或只增加日计数、月计数没增加的半完成状态。日/月 key 带日期维度，设置到周期结束后的 TTL，过期后自动清理。

需要指出的限制：上游失败仍不退额度；脚本未使用同槽 hash tag，当前单机配置不能直接照搬 Redis Cluster；Redis 主从切换可能丢失最近写入。另外，QuotaPlan 字段允许配置业务上限，当前实现按订阅加载套餐。

## 4.5 事务与幂等

`CallLogServiceImpl.saveDirect` 在一个 MySQL 事务中先用 `INSERT IGNORE` 写调用日志，再检查是否为首次插入；如果首次插入且 appId/apiId 存在，则 upsert 当日统计。日志重复投递时插入影响行数为 0，方法直接返回，不重复增加统计。

事务边界只涵盖 MySQL 操作，不包含 RabbitMQ 发布、Redis Lua 或上游 HTTP。Spring 本地事务无法自动把数据库、Redis、RabbitMQ 和 HTTP 调用变成一个原子整体。

## 4.6 分页与查询

服务层把 page 限制为至少 1、size 限制在 1 到 100 之间，并将筛选条件下推至 MyBatis-Plus 的数据库分页查询，避免一次性加载所有调用日志再在 JVM 内切页。面试可以补充：数据量继续增长时可按创建时间/ID 做游标分页，避免大 offset 越翻越慢；筛选和排序字段要有匹配索引。

## 4.7 一致性场景追问

### 两个管理员同时审批同一条订阅怎么办？

更新语句带 `WHERE status = 'PENDING'`。第一个事务成功后状态改变，另一个请求影响行数为 0，返回状态已被修改。缓存只在成功转换后失效。

### 消息重复消费会不会重复累计统计？

消息可能重复投递，因此消费者按唯一 traceId 幂等插入。只有首个插入成功的事务更新 UsageStat；重复消息发现 `INSERT IGNORE` 影响行数为 0 后返回，不再累计。

### Redis 不可用时怎么处理？

开放请求的验签 Nonce、限流和配额依赖 Redis；登录态也依赖 Redis。当前不是“Redis 故障自动放行”的设计，避免在身份或额度不可验证时绕过保护。生产化要明确 fail-open/fail-close 策略、超时、告警、降级范围和恢复后的数据补偿；不能只靠增加客户端重试。
