# 5. RabbitMQ、排障与模拟面试

## 5.1 调用日志为什么异步化？

开放 API 的主目标是及时返回上游结果。若每次请求都同步写调用日志和用量统计，数据库写入延迟、锁等待和高峰压力会直接增加用户调用耗时。当前过滤器在请求结束时构造 `CallLogMessage`，服务层将其发送到 RabbitMQ；消费者落库并更新按日统计。

```text
SignatureFilter finally
   → RabbitTemplate.convertAndSend
   → call.log.exchange / call.log.queue
   → CallLogListener 手动 ACK
   → CallLogService.saveDirect 事务写 CallLog + UsageStat
```

队列配置有死信交换机和死信队列。消费者落库成功后 ACK；处理异常时 `basicNack(requeue=false)`，消息进入死信队列，避免同一条坏消息无限重试。当前死信队列没有自动补偿消费者，需要监控和人工处理。

## 5.2 “可靠消息”怎么说才准确？

可以说项目做了多层防护：持久队列、手动 ACK、消费失败进入 DLQ、数据库事务、traceId 幂等，以及发送调用抛异常时同步写库兜底。但这些机制不等于端到端绝不丢失：

- 生产者发送调用未抛异常不必然证明消息已被 Broker 持久接收；当前没有配置 publisher confirm/return。
- 发送与主业务响应之间没有 Outbox 事务绑定；若进程在关键窗口崩溃，可能留下消息缺口。
- DLQ 只隔离失败消息，若没有告警、查因和重放流程，数据仍不会自动修复。
- 同步兜底只针对发送调用抛出的异常；不能把它描述成所有 Broker 故障都能检测到。

如果要演进到更高可靠性，可在同一数据库事务写业务数据和 Outbox 事件，再由后台投递并标记状态；或者配置可靠发布确认、有限重试/退避、告警、死信监控和可审计重放。消费者仍需幂等，因为重复投递无法完全避免。

### ACK、NACK 和拒绝重入队的含义

- ACK：确认当前消息已成功处理，Broker 可删除该投递。
- NACK 且 `requeue=true`：消息重新进入队列，可能造成失败重试循环。
- NACK 且 `requeue=false`：消息不回原队列；配置死信交换机时路由到 DLQ。

## 5.3 可观测性与排障

- `traceId` 贯穿响应头、MDC 和调用日志，便于从一次 API 请求定位日志记录。
- 调用日志保存 appId/apiId、请求方法/路径、HTTP 状态、耗时、来源 IP、错误码和请求/响应字节数。
- 管理操作用 `@AuditLog` 记录操作者、动作、资源和结果；审计写入失败不阻塞原业务。
- 看板以日统计数据为基础，调用日志用于追踪单次请求。

### 某个用户说开放 API 超时，怎么排查？

建议按 traceId 和耗时阶段逐步定位：

1. 查调用日志状态码、错误码、latency、应用和 API，确认请求是否进入平台并识别到目标。
2. 判断失败发生在入口校验（签名、IP、订阅、额度）还是上游（超时/连接失败/返回 5xx）。
3. 查服务端日志中的 traceId、上游 URL 校验结果及异常栈；确认 DNS、网络出口、代理和超时配置。
4. 如果接口已返回但日志/看板缺失，查 RabbitMQ 队列积压、DLQ、消费者错误和数据库事务异常；按 traceId 检查幂等记录。
5. 对比同一 App/API 的其他请求，确认是单请求、某上游还是系统性故障；必要时限流或临时下线上游 API。

不要仅凭 HTTP 502/504 就断言根因是网络，先确认错误码映射和日志记录。

## 5.4 高频综合场景题

### 场景一：两个并发请求同时为同一 App 和 API 创建订阅，怎么保证只产生一条？

业务层先查可以给出快速提示，但并发时仍可能同时查到不存在。最终依赖数据库 `(app_id, api_id)` 唯一索引；重复键异常转换成业务错误。拒绝后重申走旧记录的条件更新，而不是创建第二条。

### 场景二：缓存已更新但数据库事务回滚，如何避免脏数据？

写路径应先提交数据库变更，再删除缓存。更强的一致性要求可以在事务提交后发缓存失效消息或用 Binlog 订阅；还需考虑缓存重建与删除的竞态。项目采用 DB 写后删缓存，缓存与 DB 不在同一分布式事务内，主要追求最终一致。

### 场景三：QPS 通过，日配额却不足，请求会怎样？

现在 QPS 与日/月配额在同一次 Lua 中判断与扣减：令牌不足返回 0，日/月不足返回 -1/-2，且拒绝路径不写任何 key，所以不会出现“QPS 通过但配额不足、令牌被白白消耗”。脚本只保证 Redis 内的扣减原子；上游失败、超时仍不退额度，若要按成功调用计费需要另做预占/确认与幂等。

### 场景四：为什么上游返回 500 也可能消耗配额？

额度在转发前扣减，用于限制平台收到的有效调用尝试，不把上游失败自动视作“没有消耗”。若产品要求只按成功调用计费，需要设计预扣与结算/回补，处理重试、重复回调、进程崩溃和并发超限，避免简单退款把真实调用量放大。

### 场景五：怎么扩容到多实例？

Redis 保存共享登录态、Nonce、缓存与额度，MySQL 保存共享业务数据，RabbitMQ 解耦日志消费；这为多实例提供了基础。还需检查 Session/ThreadLocal 是否只用于请求内上下文（当前会在完成时清理）、定时任务是否重复执行、密钥配置是否一致、Redis/MQ 的高可用、数据库连接池容量，以及限流是否按用户/应用/全局维度正确隔离。

### 场景六：某上游 URL 被配置成 `http://127.0.0.1`，怎么处理？

管理员创建或更新 API 时先校验上游地址；每次真实转发前再次校验 DNS 解析结果和目标 IP，拒绝未授权的 loopback/private/link-local 等地址。生产关闭允许 loopback 的演示配置，并在网络出口层再做限制。还要考虑 DNS 重绑定、IPv6 地址、重定向和代理绕行等边界。

### 场景七：如何优化调用日志查询？

先看实际查询条件与 `EXPLAIN`，为 appId/apiId 与创建时间等常用筛选设计合适索引；限制分页大小并下推到数据库。随着日志规模增长，按时间归档/分区、冷数据迁移、异步导出和基于 `(create_time,id)` 的游标分页都可评估。索引和分区需要结合写入量与保留策略验证。

## 5.5 面试官可能连续追问的项目题

### 为什么不用 JWT？

本项目需要登出立即使 Token 失效，Redis Token 删除即可实现。JWT 的优势是本地校验和无状态，但即时撤销通常需要黑名单或短有效期加刷新机制。当前单体部署和登录规模下，Redis Session 的实现更直接；若未来需要服务间无状态校验，再评估 JWT 和撤销方案。

### 为什么开放调用的过滤器做了很多业务校验？

这些校验横跨签名、原始 Body、Nonce、响应包装和 finally 日志，Filter 能在 MVC Controller 前后完整包住链路；Controller 仍负责路由和调用代理 Service。若治理规则继续增多或需要独立扩缩容，可以抽成网关组件/服务，但当前不应把这个 Filter 说成 Spring Cloud Gateway。

### 有哪些可进一步完善的点？

回答 2–3 个具体点即可，并结合优先级：

- 消息可靠性：publisher confirm、Outbox、有限重试、DLQ 告警和重放工具。
- 额度：QPS 与日/月配额已在单脚本内原子扣减；仍可评估按成功调用计费的预占/确认与幂等。
- 安全：强化上游出口网络策略、DNS 绑定防护、响应大小限制和密钥轮换。
- 可观测性：队列积压、DLQ 数、限流命中率、缓存命中率、上游分位延迟和 traceId 查询能力。
- 数据增长：调用日志保留/归档策略、游标分页及慢查询治理。

说清这些是现状限制或改进方向，不要把待做项说成已经上线。

## 5.6 反问与回答收尾

被问“你负责的最大挑战是什么”时，可选一个真实的链路问题来讲：例如请求体验签与后续转发需要复用原始字节、额度并发扣减需要 Redis 原子脚本、重复消费会影响统计等。按“问题—约束—方案—验证—剩余风险”说明，避免把整个仓库所有功能都说成个人独立完成。

回答不确定的实现细节时，可以说：“我会回到当前配置/源码确认这个行为；从现有实现看，已经做到……，剩下的风险是……”。这种边界感比猜测底层实现更可靠。
